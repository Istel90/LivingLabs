## 구현 완료, 운영 적용 대기

- SQL 제안: `docs/PRIORITY_DRAFT_CONCURRENCY.sql`.
- 서버 시퀀스로 전체 저장본 번호 발급. 삭제 후 번호 재사용하지 않으며 지역별 연속번호는 보장하지 않는다.
- lineage_id와 parent_id로 한 작업 세트의 저장 이력을 연결. 현재 저장 단위는 여러 대안 탭을 포함하는 **작업 세트**이다. 개별 탭의 완전한 관계형 분리는 후속 작업이다.
- 동일 원본의 후속 저장은 유일 인덱스로 한 건만 허용한다. 다른 PC가 먼저 저장했으면 실패한 PC의 작업은 유지하고 별도 대안으로 저장하도록 안내한다. 자동 병합은 하지 않는다.
- 요청 UUID 재사용 및 ON CONFLICT DO NOTHING으로 같은 열린 화면에서 실패 후 재시도 시 중복 방지. 브라우저 종료·새로고침을 넘는 미확정 요청의 자동 복원은 아직 구현하지 않았다.
- 분석 스냅샷은 갱신 대신 새 행으로 저장. 이름 변경/삭제/복원에는 management_version 조건을 사용해 오래된 화면의 수정이 덮어쓰지 못하도록 한다.
- 기존 화면에 저장본 관리 버튼: 이름 변경, 휴지통 이동, 휴지통 조회, 복원. 기존 archived 13건도 새 관리 화면 휴지통에 표시하도록 설계했다.
- 비교의 최신본 묶음은 작성자 문자열 대신 lineage_id를 사용한다. 옛 자료는 개별 root로 유지하며 동일 작성자라는 이유로 합치지 않는다.
- Vite 빌드에서 DB 환경설정이 정적으로 치환되도록 공통 설정 읽기를 수정했다. 로컬 검증 서버 주소가 실제 빌드에 반영되는 것을 확인했다.

운영 migration은 자동 승인 검토에서 거부되었다. 이유: 운영 저장 동작 변경 및 기존 anon/authenticated INSERT 경로에 시퀀스 USAGE 권한 추가의 정확한 범위가 승인되지 않았다는 판단. 우회 적용하지 않았다. SQL과 프런트엔드를 함께 적용해야 하므로 **pages-dist 및 외부 배포는 이전 서비스 버전을 유지**한다. 새 코드를 집 PC에 가져가더라도 DB 적용 전 빌드·서비스 교체하지 않는다.

## 확인한 검증과 한계

- 실제 운영 DB 읽기: 행 수·상태·컬럼·외래키·RLS 확인. 변경 후 archived=13, draft=0 확인.
- 로컬 PostGIS의 별도 임시 스키마: 실제 SQL에서 스키마명만 바꾸고 역할 GRANT/REVOKE를 제외해 검증. 테스트 스키마는 종료 시 제거한다. 기존 분석 데이터는 변경하지 않는다.
- 10개 병렬 새 저장의 번호 고유성, 같은 부모 병렬 저장 1개 성공/1개 충돌, 확인된 요청 재시도, 동시 메타데이터 변경 1개 성공, 삭제된 원본 저장 거부/복원 후 저장, 스냅샷 변경 금지, 다른 재해 부모 거부 통과.
- 서비스 요청 테스트 및 기존 지역별 조회·겹침 계산 테스트 통과.
- 격리된 4181 검증용 메모리 API와 실제 빌드로 홍수 관리 화면의 이름 변경·휴지통 이동·복원 확인. 이는 운영 DB 쓰기 검증이 아니다.
- 홍수·폭염 빌드 성공. 운영 DB 시퀀스 권한/RLS로 실제 저장, 운영 신버전 화면 및 외부 배포 검증은 미수행이다.

## 전체 시스템 연결 순서

1. **저장 계약 안정화:** 이번 변경 적용과 운영 동시 저장 검증. 프런트만 먼저 배포하지 않는다. 이전 브라우저는 새로고침한다.
2. **계정·조직 권한:** 실제 로그인 계정을 auth.users와 연결하고 프로젝트/부서 멤버십으로 RLS를 제한한다. 현재 테이블에는 anon/authenticated에 true 조건의 읽기·쓰기 정책이 있다. 작업자 입력 문자열을 권한으로 사용해서는 안 된다. 이번 변경은 로그인·소유권 분리를 구현하지 않는다.
3. **대안·권역 관계형 저장:** priority_area_sets → priority_area_options → parcel_candidates/candidate_parcels → selected_priority_areas를 하나의 트랜잭션으로 저장한다. 옵션 UUID와 원본 데이터 버전, 모델·가중치, 분석 실행 ID를 참조한다. JSONB에는 재현용 조건과 스냅샷을 남기며 모든 격자값을 무조건 행으로 풀지 않는다.
4. **검토·사업 이력 연결:** 실제 검토 전달 경로 platform_handoffs를 handoff_requests·project_review_packages·review_events와 연결한다. 접수/회수/선정 전이를 SQL 함수로 검증하고 중복 요청 키를 둔다. 이름 변경·복원까지 포함한 append-only 감사 이력을 추가한다.
5. **분석 데이터·성능:** 대용량 격자/공간분석은 기존 PostGIS 유지. 데이터셋 카탈로그·버전·출처·파일 체크섬·작업 상태를 SQL로 관리한다. 래스터 파일은 파일 저장소에 유지하고 필요한 공간 조회에 GiST 및 지역/시점 인덱스를 사용한다. Supabase로 전국 원자료를 전량 이전하는 것은 별도 용량·비용 검토 후 결정한다.
6. **운영:** 스키마 변경 기록, 테스트 DB, 복구 절차, 서비스 계정 분리 및 백업 복구 검증을 갖춘다. 두 PC에서는 같은 변경 스크립트를 공유하며 DB 변경은 한 번만 적용한다.

## 승인 후 적용 순서

1. 운영 DB의 신규 저장/컬럼 변경 여부 재확인, 최신 백업.
2. 검토된 SQL을 Supabase migration으로 적용. 기존 읽기·쓰기 RLS는 확대하지 않는다. 시퀀스 사용 권한만 기존 INSERT 역할에 부여한다.
3. 작은 별도 검증용 저장본으로 운영 권한·충돌 처리 확인, 검증 자료만 정리.
4. PAGES_BASE_PATH=/internal-tools로 빌드하고 pages-dist/internal-tools 반영. DB 설정이 운영 URL인지 확인.
5. 정확한 4173 홍수 기준 화면, 폭염, 실제 저장 API와 served build 확인. 외부 배포는 별도 수행·확인.
6. 새 관리 화면에서 archived 13건이 휴지통에 있고 기본 목록은 비어 있는지 확인.

운영 SQL 승인 전 상태에서 전체 시스템 SQL 전환이 완료됐다고 보고하지 않는다.
